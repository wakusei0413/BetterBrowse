# 阶段二：WebDAV 云端同步（延后，需补齐协议设计后评审）

> 配套总览见 [00-overview.md](./00-overview.md)。本阶段**默认延后**，在 `01-local-indexeddb.md` 阶段一完成且真实需求验证后，先补齐本文列出的未定义协议，再评审启动。

## 1. 设计目标（沿用原始计划）

- 跨设备单向/双向同步收纳数据；
- 不可变操作日志 + 周期快照，而非上传数据库文件；
- `deviceId + sequence` 排序，字段级合并，冲突不静默覆盖；
- 墓碑同步 + 30 天回收站，90 天设备退役；
- WebDAV 凭据不进入同步对象。

## 2. 远端目录结构（沿用）

```
/BetterBrowse/
  manifest.json           # 最新清单（指向最新 generation 的批次与快照）
  generations/
    gen-0001-batch.jsonl  # 追加式操作日志（每个操作一条 JSON 行）
    gen-0001-snapshot.json# 该代基线全量快照
    gen-0002-batch.jsonl
    ...
  devices/
    <deviceId>.json       # 每台设备最后确认序列号
  tombstones/
    <entityId>.json       # 30 天回收站
```

写入使用 `ETag` / `If-Match` 条件写；清单更新采用 `deviceId + sequence + operationId` 排序。

## 3. 必须补齐的未定义协议（评审门槛）

原始计划给了目录与原则，但缺少以下可执行协议。**未补齐前不应开工**。

### 3.1 快照与日志的衔接协议

- 应用某代快照基线后，该代 `batch.jsonl` 中的操作如何继续重放？`generation` 基线推进条件？；
- 快照损坏/缺失时的回退路径（回退到上一代快照？还是从零重建？）；
- 新设备加入时"从最新快照重新配对"的全量应用流程。

### 3.2 云端原子性 / 不一致恢复协议

- WebDAV 无事务，`manifest.json` + 批次文件 + 快照文件三者无法原子更新；
- 必须定义：清单指向了"只上传一半的快照"或"批次缺失"时的检测与恢复流程；
- 定义远端状态不一致（清单与文件实际不符）的检测手段与自愈步骤。

### 3.3 字段级合并算法

- 操作日志为 append-only，"同一字段最新版本"的判定规则（per-field last-writer-wins 的版本来源？）；
- "同字段冲突不静默覆盖"与 LWW 的边界：冲突记录的数据结构、用户如何裁决；
- 设置类冲突"采用云端值"的含义——两台设备均离线改设置时谁是"云端"？需给出确定性裁决规则。

### 3.4 日志无限增长治理

- 按"已确认设备都达到该基线才清理旧日志"规则，存在离线设备 > 90 天时日志无法清理；
- 需给出远端配额上限、超期强制压缩策略、以及"退役设备回归"的补齐机制。

## 4. 其他待定项

- 同步内容为完整 URL 历史，涉及浏览隐私，UI 需显式提示"URL 列表将上传到你的 WebDAV"；
- 手动同步触发、同步状态展示、冲突查看与裁决界面；
- 本地快照与云端数据冲突时，谁优先的恢复策略。
